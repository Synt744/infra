# Архитектурные решения

Для каждого решения: что, почему, альтернативы, последствия.

---

## 1. Ansible как единственный оркестратор

**Решение:** Весь процесс провижининга управляется Ansible.

**Почему:**
- Идемпотентность из коробки — повторный запуск не ломает систему
- Нет агента на целевой машине (agentless over local connection)
- Декларативный подход с огромной экосистемой модулей
- Человекочитаемый YAML, понятный спустя годы

**Альтернативы:**
- *Chef/Puppet* — требуют агентов, сложнее для одиночной машины
- *Shell-скрипты* — не идемпотентны, превращаются в хаос при росте
- *Nix/NixOS* — максимальная воспроизводимость, но высокий порог входа и несовместимость с Debian

**Последствия через годы:**
- Ansible развивается стабильно, риск поломки API минимален
- Любой DevOps-инженер поймёт репозиторий без документации

## 2. Docker как платформа сервисов

**Решение:** Все сервисы (MetaMCP, Dockge, будущие) живут в Docker Compose стеках в `/opt/stacks/`.

**Почему:**
- Изоляция: каждый сервис в своём контейнере, своём сетевом неймспейсе
- Воспроизводимость: `docker compose up` — и сервис работает
- Простота обновления: `docker compose pull && up -d`
- Dockge даёт UI без Portainer (более лёгкий, без лишних абстракций)

**Альтернативы:**
- *Podman + systemd units* — лучше с точки зрения безопасности (rootless), сложнее в эксплуатации
- *systemd-nspawn* — нативно для systemd, слабая экосистема образов
- *k3s/k8s* — избыточно для рабочей станции

**Правило Ansible:**
Ansible не управляет контейнерами напрямую — только `docker compose up`.  
Это разделяет ответственность: Ansible раскладывает конфиги, Docker управляет контейнерами.

## 3. MetaMCP как MCP-агрегатор

**Решение:** MetaMCP вместо mcp-proxy или supergateway.

**Почему:**
- `mcp-proxy` и `supergateway` проксируют один stdio-сервер → один контейнер/порт
- MetaMCP агрегирует N stdio-серверов в один HTTP/SSE endpoint с Bearer-аутентификацией
- Веб-UI в духе Dockge: серверы → namespace → endpoint
- Единый токен для всех агентов

**Альтернативы:**
- *Отдельный порт на каждый MCP-сервер* — множество портов, сложная конфигурация агентов
- *Собственный FastAPI прокси* — велосипед, нужно поддерживать

**Почему Streamable HTTP (`/mcp`) вместо SSE (`/sse`):**
В `hermes-agent` открытый баг: SSE-транспорт теряет session ID → `Missing session ID`.  
OpenCode тоже имел нестабильность с SSE в remote-режиме.  
`/mcp` (Streamable HTTP) надёжнее для обоих агентов прямо сейчас.  
SSE сохраняется как резервный вариант в документации.

**Важно:** `APP_URL` в `.env` — реальный IP/hostname, не `localhost`.  
MetaMCP жёстко валидирует CORS по этому URL.

## 4. gocryptfs для шифрования Obsidian vault

**Решение:** gocryptfs как бэкенд шифрования, не CryFS.

**Сравнение:**

| Параметр | gocryptfs | CryFS |
|---|---|---|
| Шифрование метаданных | ❌ (имена файлов шифруются, но структура видна) | ✅ полное |
| Производительность | ✅ высокая | ⚠️ умеренная |
| Уровень файлов | ✅ один файл → один зашифрованный | ✅ блочное хранилище |
| Совместимость с git-backup | ✅ (изменился файл → изменился один зашифрованный) | ⚠️ (CryFS блоки) |
| Debian пакет | ✅ `apt install gocryptfs` | ✅ `apt install cryfs` |
| Активная поддержка | ✅ | ⚠️ медленно развивается |

**Почему gocryptfs:**
- Производительность важнее полного сокрытия метаданных для личного vault
- Лучше совместим с инкрементальными бэкапами (Restic видит изменения на уровне файлов)
- Быстрее монтируется

**Для максимальной приватности:** CryFS — лучший выбор (переключается через `obsidian_crypto_backend: cryfs`).

**Схема работы:**
1. `kdialog` запрашивает пароль (нативный KDE-диалог, не terminal)
2. `gocryptfs` монтирует зашифрованную директорию в `~/Obsidian`
3. Запускается Obsidian AppImage с путём к `~/Obsidian`
4. При закрытии Obsidian — `fusermount -u` размонтирует vault

## 5. Restic для бэкапов

**Решение:** Restic вместо Borg или rsnapshot.

**Сравнение:**

| Параметр | Restic | Borg | rsnapshot |
|---|---|---|---|
| Дедупликация | ✅ content-addressed | ✅ | ❌ |
| Шифрование | ✅ встроено | ✅ встроено | ❌ |
| Бэкапы на удалённые хосты | ✅ sftp, S3, rclone | ✅ только Borg-сервер | ✅ rsync |
| Официальный Debian пакет | ✅ | ✅ | ✅ |
| REST API / интеграции | ✅ | ⚠️ | ❌ |
| Скорость | ✅ | ⚠️ (медленнее для больших данных) | ✅ |

**Почему Restic:**
- Нативная поддержка множества бэкенд-хранилищ (SFTP, S3, Backblaze, rclone)
- Атомарные снапшоты, безопасная параллельная работа
- Встроенное шифрование — нет отдельного слоя
- systemd timer заменяет cron, лучшая интеграция с journalctl

## 6. Разделение данных и конфигурации

**Решение:** `/opt/` разделён по назначению.

```
/opt/stacks/    — Docker Compose проекты (конфигурация, managed by Ansible)
/opt/data/      — персистентные данные контейнеров (volumes)
/opt/backups/   — локальные бэкапы
/opt/cache/     — кэш (исключён из бэкапа)
/opt/tmp/       — временные файлы (исключён из бэкапа)
```

**Почему важно:**
- Ansible может пересоздать `/opt/stacks/` из репо — это не данные
- `/opt/data/` — данные Postgres, MetaMCP — бэкапятся
- Чёткое разделение избегает случайного удаления данных при пересоздании конфигурации

## 7. Ansible Vault для секретов

**Решение:** Все секреты в `ansible/group_vars/all/vault.yml`, зашифрован ansible-vault.

**Почему не:**
- *HashiCorp Vault* — избыточно для рабочей станции
- *pass / gpg-encrypted files* — требуют дополнительных инструментов в bootstrap
- *Открытый текст в репо* — очевидно нет

**Паттерн:**
- `vault.yml` в `.gitignore` — никогда не попадает в репо
- `vault.yml.example` в репо — шаблон с `CHANGE_ME`
- Переменные с префиксом `vault_*` используются в шаблонах

## 8. Профили вместо отдельных плейбуков

**Решение:** Один мастер-плейбук + профили с переменными.

**Почему:**
- Один источник истины для порядка применения ролей
- Профиль = только набор `install_*: true/false`
- Новая машина = новый профиль (3-5 строк), без копирования логики

**Расширяемость:**
- Добавить новую роль = 1 строка в `workstation.yml` + переключатель
- Не нужно менять 4 профиля при добавлении одной роли
